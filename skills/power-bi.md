# Power BI・DAX・レポート設計

[rules/power-bi.md](../rules/power-bi.md)を適用する。モデルへ接続できない場合は、テーブル・列・型・粒度・リレーション・既存メジャーの提示を求め、確認できた情報だけで設計する。

## モデル

- ファクトとディメンション、キーの一意性、日付テーブル、フィルター方向を確認する。
- スタースキーマ、多対一・単方向を基本とし、例外は要件と理由を示す。
- 業務用語を名前と説明へ反映し、技術キーの表示・非表示を整理する。
- Import / DirectQuery / Direct Lakeはデータ量・鮮度・基盤・制約で比較する。採用を自動決定しない。
- RLS、接続先、権限、更新方法を確認する。権限変更や公開を文案作成と混同しない。

## DAX改善

1. 元式の目的、期待値、使用するビジュアル、フィルター条件を確認する。
2. 繰り返し計算、コンテキスト遷移、過剰な反復、フィルターの範囲を調べる。
3. VAR / RETURN、名前付きメジャー、DIVIDEを使い、BLANKの意味を維持する。
4. COUNTとCOUNTROWS、VALUESとSELECTEDVALUEを意味の確認なしに置換しない。
5. 行・小計・総計、単一選択・複数選択・無選択、データなし、分母0で前後を比較する。
6. 速度改善は実測前には仮説として示す。実測では同条件の処理時間とクエリを記録する。

## レポート設計

利用者・判断・閲覧時間・ページ数・利用可能な列を先に決める。ページごとに概要、監視、原因分析、説明、比較のどれを担うかを定める。
配色、フォント、余白、凡例、指標の順番、スライサー位置、ドリルスルー、読み上げ用説明を具体化する。
標準ビジュアルを先に使い、Deneb等を使う理由を残す。図表の順位と色はページ間で統一する。色だけで状態を区別しない。
設計案の完成とPBIR作成・Power BIでの表示確認は別工程として報告する。

## 確認

モデル接続、DAX実行、ファイル保存、Desktop再読込、RLS、公開・更新を個別に記録する。M365にMarkdownを渡しただけでモデルを編集済みとしない。
